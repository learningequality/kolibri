============================
QR code sign-in for learners
============================

This how-to explains how to enable and operate the **QR code sign-in** feature
for learners in a Kolibri facility. QR code sign-in lets young learners sign
in by holding a printed credential card up to a device camera, instead of
typing a username and password.

.. note::

   QR code sign-in is currently behind an **English-only** feature flag, the
   same gate used for picture-password sign-in and attendance-taking. It will
   be unlocked for other languages in a future release once the icon/card
   strings have been translated.

When to use QR code sign-in
===========================

QR code sign-in is a good fit when:

- Learners are young children who struggle with usernames and passwords.
- Learners share devices (a class cart of tablets, a library kiosk, etc.).
- A coach or admin can print and hand out credential cards.

It **coexists** with all other sign-in methods (username+password, username
only, picture password). Enabling QR does not disable any other method.

Threat model
============

The QR code encodes a per-learner random **bearer token** (256 bits of
entropy, generated by ``secrets.token_urlsafe(32)``). Anyone who photographs a
learner's card can sign in as that learner until the token is rotated.

This is the same threat model as the existing picture-password feature, but
the keyspace is dramatically larger (256 bits vs. ~10 bits for picture
passwords), so brute-force guessing is computationally infeasible. The feature
is designed for shared-device classroom use; it is **not** appropriate for
high-stakes assessments or for facilities where learners might maliciously
photograph each other's cards.

Tokens can be rotated (regenerated) on the backend if a card is lost or
suspected compromised — see *Rotating a learner's token* below.

Enabling QR code sign-in
========================

1. Sign in as a facility admin.
2. Open **Facility > Settings**.
3. Under the **Facility** section, check **"Allow learners to sign in with a
   QR code (English only)"**.
4. Click **Save**.

When you save, Kolibri:

- Generates a unique QR token for every existing learner in the facility who
  doesn't already have one (role-less, non-superuser learners).
- Leaves existing tokens alone if you disable and later re-enable the feature.

A progress indicator may be shown if your facility has many learners; the
bulk-assignment task runs in the background.

Printing learner QR cards
=========================

After enabling the feature:

1. As a coach or facility admin, navigate to the **Learners** tab (coach) or
   **All passwords** page (facility admin).
2. Click **Print**.
3. In the print-format dialog, select **"Print QR codes"**.
4. Click **Continue** to open your browser's print dialog.

Each printed card contains:

- A box for the learner's photo (so the card can be matched visually).
- The learner's full name and username.
- The QR code itself.

The cards are designed to be cut out and laminated. Print on stiff paper for
durability.

Signing in with a QR code
=========================

At the sign-in screen, a learner (or coach on their behalf):

1. Click the **"Sign in with a QR code"** link on the sign-in page (visible
   only when QR sign-in is enabled).
2. Hold the credential card in front of the device camera so the QR code
   fills the on-screen viewfinder.
3. When the QR code is read, a confirmation modal appears showing the
   learner's full name and asking **"Is this you?"**
4. The learner taps the check button to sign in, or the X button to go back
   and try a different card.

If the camera is unavailable (the device has no camera, browser permission
was denied, or the deployment is over plain HTTP on a non-localhost origin),
the page automatically falls back to a **"Upload a photo"** button. The
learner (or a coach) can take or choose a photo of the QR code; the page
decodes the image and proceeds with the same confirm flow.

HTTPS requirement (important)
=============================

For security reasons, browsers only allow camera access (``getUserMedia``)
in a **secure context** — HTTPS or ``localhost``. Kolibri is frequently
deployed over plain HTTP on a LAN IP, which is **not** a secure context.

This means that on a plain-HTTP deployment:

- The live camera view will not start.
- The learner will land directly on the **"Upload a photo"** fallback.

To enable live camera scanning, deploy Kolibri behind an HTTPS reverse proxy.
See the Kolibri deployment guide for nginx/Apache configuration examples.

The **file-upload fallback works in any context**, so QR sign-in is usable on
every Kolibri deployment — but the live-camera UX is only available over
HTTPS.

Android app support
===================

The Kolibri Android app wraps Kolibri in a WebView. The file-upload fallback
described above works inside the WebView **without any changes** — a learner
(or coach) can always pick or capture a photo of a QR code and have it
decoded. However, the **live-camera scanner** does not work out of the box,
because WebView will not open the device camera unless the host app does two
things: declare the camera permission, and grant the WebView's permission
request at runtime.

These changes live in the Android wrapper repo,
`learningequality/kolibri-installer-android <https://github.com/learningequality/kolibri-installer-android>`_,
not in this repository.

Manifest declarations
---------------------

Add the camera permission and a (non-required) hardware feature declaration
to ``AndroidManifest.xml``:

.. code-block:: xml

   <uses-permission android:name="android.permission.CAMERA"/>
   <uses-feature android:name="android.hardware.camera" android:required="false"/>

Declaring the hardware feature with ``android:required="false"`` ensures the
app is still installable on devices without a camera (the file-upload
fallback is used there).

WebChromeClient override
------------------------

WebView routes JavaScript permission requests (such as
``navigator.mediaDevices.getUserMedia()``) through
``WebChromeClient.onPermissionRequest()``. The default implementation
**denies** these requests, so the camera never starts. You must override it
and grant the video-capture resource:

.. code-block:: java

   webView.setWebChromeClient(new WebChromeClient() {
       @Override
       public void onPermissionRequest(PermissionRequest request) {
           request.grant(request.getResources());
       }
   });

For a tighter scope, grant only the video-capture resource explicitly:

.. code-block:: java

   @Override
   public void onPermissionRequest(PermissionRequest request) {
       for (String resource : request.getResources()) {
           if (PermissionRequest.RESOURCE_VIDEO_CAPTURE.equals(resource)) {
               request.grant(new String[]{ PermissionRequest.RESOURCE_VIDEO_CAPTURE });
               return;
           }
       }
       request.deny();
   }

Runtime permission prompt (Android 6+ / API 23+)
-------------------------------------------------

Even with the ``WebChromeClient`` override granting the request, on
**Android 6.0 (API 23) and above** the app must hold the ``CAMERA``
permission at runtime. The first time a learner opens the QR scanner, the
system shows the standard "Allow [app] to take pictures and record video?"
prompt. If the learner grants it, the live camera view starts; if they deny
it, the page falls back to the **"Upload a photo"** button automatically —
no extra handling is needed.

The host app should request ``Manifest.permission.CAMERA`` at runtime
(e.g. via ``ActivityCompat.requestPermissions()``) either proactively at
launch or lazily when the WebView first asks for the camera. If the app
targets API 22 or lower, runtime prompts are not shown and the permission
is granted silently at install time.

Summary
-------

- Without **any** Android-side changes: file-upload fallback works, live
  camera does not.
- With manifest permission + ``WebChromeClient.onPermissionRequest()`` grant
  + runtime permission prompt accepted: live-camera scanner works inside the
  WebView.

Rotating a learner's token
==========================

If a learner's card is lost or compromised, an admin can rotate the token via
the Python API:

.. code-block:: python

   from kolibri.core.auth.utils.qr_tokens import reassign_qr_login_token
   from kolibri.core.auth.models import FacilityUser

   user = FacilityUser.objects.get(username="maria", facility=facility)
   reassign_qr_login_token(user)
   # The old card no longer works. Print a new card for the learner.

Promoting a learner to a coach or admin role automatically clears their QR
token (a user with a role is no longer a learner for QR-login purposes).
Demoting them back to a learner automatically assigns a fresh token if the
facility has QR login enabled.

How sign-in is validated
========================

The sign-in flow uses two passes to prevent a learner from accidentally
logging in as someone else whose card they happened to scan:

1. **Pre-validate**: The decoded token is sent to the session endpoint with
   ``?prevalidate=true``. The server resolves the token to a learner and
   returns the learner's full name **without creating a session**.
2. **Confirm**: The learner confirms "Yes, sign in" in the modal. The token
   is then sent again (without ``prevalidate``) and the real session is
   created.

A failed QR-token authentication **never falls through** to
username/password authentication, even if username/password fields are also
present in the request. This is enforced in
``CreateSessionSerializer.validate``.

Sync behaviour
==============

QR tokens are part of the ``FacilityUser`` morango model and sync across
devices like any other facility data. When new learners arrive via sync into
a facility with QR login enabled, the receiving device automatically tops up
any missing tokens (see ``QRLoginSyncHook`` in
``kolibri/core/auth/kolibri_plugin.py``).

Token collisions are astronomically unlikely (256-bit random tokens) and are
not specially handled in the sync layer; a hard ``IntegrityError`` would
surface in that impossible case.
